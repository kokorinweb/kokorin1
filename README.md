# Osteria Bellini

Сайт итальянского ресторана с корзиной, ИИ-консультантом и Telegram-ботом. Один репозиторий,
один деплой, одно меню на все каналы.

## Что внутри

| Часть | Где | Что делает |
| --- | --- | --- |
| Сайт | `src/app` | Главная, меню с фильтрами, корзина и оформление заказа |
| ИИ-консультант на сайте | `src/components/ChatWidget.tsx` + `src/app/api/chat` | Отвечает по меню и **сам кладёт блюда в корзину** через tool use |
| Telegram-бот | `src/lib/telegram.ts` + `src/app/api/telegram` | Команды и тот же ИИ-консультант в личке |
| Заказы | `src/app/api/order` | Валидация, пересчёт цен на сервере, запись в базу, уведомление в рабочий чат |
| Панель заказов (CRM) | `src/app/admin` | Сводка с графиками, стол заказов, статусы, поиск, выгрузка в CSV |

Ключевая идея: **меню задано ровно в одном месте** — `src/lib/menu.ts`. Витрина, валидация
заказа, промпт ИИ и ответы бота читают его оттуда. Правила доставки так же живут только в
`src/lib/restaurant.ts`. Цены нигде не дублируются, поэтому разъехаться им негде.

Исключение ровно одно и оно намеренное: **строки заказа хранят снапшот** названия, категории
и цены на момент оформления (`order_lines`). Цену в меню меняют деплоем, а заказ прошлого
месяца от этого дорожать не должен.

## Запуск

```bash
npm install
cp .env.example .env.local   # и заполнить ключи
npm run db:seed              # демо-заказы за 60 дней, чтобы панель не была пустой
npm run dev                  # сайт на http://localhost:3000
npm run bot                  # в отдельном терминале: бот через long polling
```

Без `ANTHROPIC_API_KEY` сайт и корзина работают полностью, а чат честно отвечает, что
консультант недоступен. Без `TELEGRAM_BOT_TOKEN` заказы просто пишутся в лог сервера.
Без `ADMIN_PASSWORD` панель заказов закрыта целиком — в ней телефоны и адреса гостей,
поэтому пароля по умолчанию здесь нет.

## Панель заказов

`/admin`, вход по `ADMIN_PASSWORD` (одна общая роль «сотрудник смены», cookie на 12 часов).

- **Сводка** — выручка, заказы, средний чек, отмены с сравнением к прошлому периоду;
  выручка по дням (за «сегодня» — по часам); продажи по категориям меню; топ блюд.
- **Заказы** — плитки по стадиям кухни, поиск по номеру, имени и телефону, фильтр по способу
  получения, смена статуса, карточка заказа с составом и историей переходов, выгрузка в CSV.

Жизненный цикл заказа задан в одном месте — `src/lib/status.ts`:

```
доставка:  новый → принят → готовится → в пути → выдан
самовывоз: новый → принят → готовится → готов к выдаче → выдан
```

Отменить можно с любого шага до выдачи. Недопустимые переходы отбивает база, а не интерфейс:
двое менеджеров из двух вкладок не уведут заказ по двум разным путям.

Числа на сводке — только те, которые проект действительно может посчитать. Посетителей сайта,
чистой прибыли и способа оплаты здесь нет: аналитики в проекте нет, себестоимости блюд в меню
нет, а оплата — курьеру или на кассе. Плитка, показывающая выдуманное число, хуже отсутствующей.

Палитра графиков проверена валидатором на различимость при дальтонизме, а не подобрана на
глаз; порядок цветов в `src/components/admin/palette.ts` менять нельзя, не перепроверив.

## База

Диалект — Postgres, драйвер выбирается переменной окружения:

| `DATABASE_URL` | Что используется |
| --- | --- |
| задан | Настоящий Postgres: Neon, Supabase, свой сервер. Так же на Vercel |
| пусто | PGlite — тот же Postgres в WASM, файлы в `.data/pgdata`. Ноль установки |

Схема применяется на старте процесса (`src/lib/db/schema.ts`, всё через `IF NOT EXISTS`).
Важное ограничение локального режима: каталог PGlite держит **один процесс**, поэтому
`npm run dev` и `npm run db:seed` одновременно не работают. Нужен доступ из нескольких
процессов или serverless — задайте `DATABASE_URL`.

Падение базы не отменяет заказ: если запись не удалась, заказ всё равно уйдёт в рабочий чат
в телеграме и клиент получит номер. Потерять живого клиента из-за недоступной CRM хуже, чем
потерять строку в таблице.

## Деплой

Сайт — обычное Next.js-приложение (Vercel, Docker, что угодно). После деплоя один раз
привязываем вебхук бота:

```bash
curl "https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://ваш-домен/api/telegram&secret_token=<TELEGRAM_WEBHOOK_SECRET>"
```

Отдельный процесс для бота в продакшене не нужен — он живёт в том же приложении.

## Чего здесь осознанно нет

Это работающий MVP, а не готовая к бою система. Не сделано:

- **Онлайн-оплата.** Заказ подтверждает менеджер, оплата курьеру или на кассе.
- **Редактор меню в админке.** Меню правится в коде и деплоем — и это осознанно: от него
  зависят витрина, валидация цен, промпт ИИ и ответы бота. Перенос меню в базу — отдельная
  задача, а не часть панели заказов.
- **Учётные записи сотрудников.** Один общий пароль смены, без ролей и без «кто отменил
  заказ». В историю статусов пишется «менеджер». Понадобится точнее — нужна таблица `users`.
- **Кнопки статуса в телеграме.** Уведомление о заказе приходит в рабочий чат, но двигать
  статус пока можно только в панели.
- **Общее хранилище состояния.** Лимитер запросов и история диалога бота лежат в памяти
  процесса. На одном инстансе это работает; на нескольких репликах или в serverless
  контекст бота будет теряться — тогда нужен Redis/KV (база для этого уже есть).
- **Бронирование столиков.** ИИ намеренно переводит такие вопросы на телефон.

## Безопасность и ИИ

- Браузер присылает только `itemId` и количество. Все цены и скидки считает сервер по `MENU` —
  подделать сумму через DevTools нельзя.
- Промпт запрещает выдумывать блюда, цены и акции; всё меню целиком лежит в контексте.
- Инструмент `add_to_cart` проверяет, что блюдо существует, до того как что-то попадёт в корзину.
- Вебхук Telegram защищён `secret_token`.
- `/api/chat` и `/api/order` ограничены по частоте запросов с одного адреса.
- Панель заказов закрыта cookie-сессией с подписью HMAC; пароль сверяется без утечки по
  времени, попытки входа ограничены по частоте. Без `ADMIN_PASSWORD` раздел недоступен.
- `/admin` закрыт от индексации, выгрузка CSV проверяет сессию отдельно от страниц.
